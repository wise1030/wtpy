## 0. 摘要（结论先行）

### 0.1 总体评价

本项目的工程质量在同类 CTA 项目中属上乘：纯逻辑引擎与框架壳分离、
决策-确认两段式、可插拔过滤器、双层风控、三级成交证据链、真值源与
幽灵仓自愈——这些设计均经过十数次真实事故的迭代验证。测试 386 例
全绿（9.9s），CI 覆盖 py3.9-3.11 + ruff + 覆盖率门槛 70%，文档体系
（4 份 docs + README）完整。生产侧 12 策略连续 5 个交易日零事故运行。

**未发现 P0 级业务逻辑错误**。信号状态机、风控闸门、执行记账三链在
测试与实盘双重验证下口径自洽。

## 2. 架构审阅

### 2.1 分层评价

```
┌─ 研究/回测层: runBT / run_matrix / run_walkforward / run_slippage_sens  (独立进程)
├─ 数据管道层: scripts/update_{contracts,hots,hot_daily} + fetch_data_*    (定时器)
├─ 部署层:     make_deploy → deploy_tpl/run.py(runDt.py) → systemd+WatchDog
├─ 策略壳层:   StraTurtle (生命周期/执行/自愈/遥测)  ← 问题集中区
├─ 过滤层:     filters/ (协议+注册表+4 内置, 生产未启用)
├─ 风控层:     RiskManager (单品种/组合/保证金/单位/账户资金 五道预算)
├─ 引擎层:     TurtleEngine (纯逻辑状态机)         ← 质量最高
└─ 数据访问层: helpers/{indicators,CsvDataLoader,DataChecker,BarJournal,LiveTruth}
```

分层方向正确；问题在于**策略壳层职责过载**（见 A1）与**部署产物管理粗放**
（见 A2-A4）。

### 2.2 架构级问题

#### A1. StraTurtle God class（2324 行 / 90 方法 / 11 类职责）——P1

单文件混合了：框架生命周期、图表、执行路由（单/双系统两套）、风控
门控、过滤器调用、真值源管理、成交回填、幽灵自愈、执行单元自愈、
持久化（2 处重复构建快照）、K线旁路日志、资金旁路落盘、涨跌停检测。

**风险**：修改任意一类职责都可能触及全部测试面；历史上"session 路径
漏挂 reanchor"类漂移正是巨型镶套结构的产物（P1-8 收敛 `_eval_core`
只解决了一半——评估路径收敛了，执行/自愈路径没有）。

**拆分蓝图**（建议按此顺序，每步保持测试全绿）：

| 新模块 | 迁出内容 | 预估行数 |
|---|---|---|
| `StraTurtleCore`（留守） | 生命周期/图表/组装 | ~450 |
| `exec/ExecutionRouter` | `_execute`/`_execute_dual`/`_size_and_cap`/`_apply_*_gates`/`_run_filter_chain`/`_reject_trigger`/`_persist` | ~550 |
| `exec/FillTracker` | `_fill_pending`/`_fill_confirmed`/`_reanchor_*`/`_maybe_ghost_trim`/`_maybe_exec_recover` | ~450 |
| `exec/TruthMonitor` | `_truth_*`/`_periodic_truth_check`/`_account_available`/`_reconcile` | ~350 |
| `exec/Telemetry` | `_alert`/`_veto_log`/`_dump_fund_live`/journal 桥接 | ~200 |

拆分时每模块以**构造注入**拿 context 访问器与引擎引用；接口边界即
测试边界（现有测试大多以假 context 驱动，迁移成本低）。

#### A2. 源码树存在双份（deploy/ 陈旧快照）——P1

- 根目录 `deploy/cta_turtle/`（396K，gitignored）为 **9/20 的旧快照**：
  StraTurtle 2221 行 vs 当前 2324 行，缺 9/21-10/9 全部修复（真值链
  重构/ghost trim/方案B 等）；
- 危害：误在此目录修改/打包/对照，即引入两代前的代码；与线上
  `/home/ubuntu/projects/cta_turtle/deploy/cta_turtle/` 易混淆。
- 处置：删除该目录，统一由 `make_deploy.py` 生成到临时/输出目录，
  或纳入 `--verify` 清单并在 README 标注其用途。

#### A3. 监控监管进程（runMonSvr）不在部署链——P1

- `make_deploy.py` 只同步 `deploy_tpl/statemonitor.yaml`，**不同步
  runMonSvr.py**；但 `wt-turtle-monitor.service:14` 的 ExecStart 指向
  `@PREFIX@/cta_turtle/runMonSvr.py`（服务器上手工维护的副本）；
- 后果：灾难重建时该 unit 将起不来（Restart=always 变重启循环）；
  且服务器上的副本与仓库副本存在漂移窗口无人知。
- 处置：把 runMonSvr.py 纳入 make_deploy（放到 deploy/ 下），unit
  路径随之修正；或明确文档化"monitor 目录独立维护"并纳入备份清单。

#### A4. 运行时数据与代码同树——P2

`generated/` `Logs/` `stradata/` 与代码同级；其中 `stradata/` 残留
手术备份（`turtle_CZCE_CF_HOT.json.ghostfix.bak` 等）会被通配工具
匹配（本报告审阅过程中已实际踩到一次）。建议：备份文件统一放
`backup/` 子目录或加明确后缀白名单；文档化清理规则。

#### A5. 多进程写同一文件无锁——P1（BarJournal）

`BarJournal.merge_rows`（helpers/BarJournal.py:168-229）"先读 max
再 append" 非原子：run.py `_auto_repair`、hotdaily、手工 fetch 三个
写者可并发写同一 `storage/csv/<code>_d.csv`，无文件锁 → 幂等仅在同
进程串行时成立。生产上三者时间窗基本错开（20:40 前手工），但无强制
保护。建议 `fcntl.flock` 或写者收敛。

### 3.2 核心三链审阅结论

**信号链（TurtleEngine）**：边沿触发、两段式确认、棘轮 N、sim 单
推进、fail-safe 双口径互补——全部有注释出处与单测覆盖。`on_price`/
`check_bar` 的止损→通道→加仓判序、跳空按开盘价、同 bar 出场不评估
入场（防乐观偏差）均正确。

**执行链（StraTurtle）**：记账价=决策价 + 成交后回写（逐笔优先/净均
价兜底）、幽灵 trim 只缩量、ghost 当日封锁、exec recover 每日一次
marker 闸——与生产事故一一对应。**双系统路径（`_execute_dual`）为
休眠代码**（生产全单系统），但被测试与配置支持，其门控逻辑与单系统
路径并行维护（B4）。

**风控链（RiskManager）**：五道预算（per_market / total_risk /
margin-sid / units / account_gate）逻辑清晰。`cap_entry` 的 share
缩放（双系统）与 sid 分组（方案B）正确；`booked_risk(stop=...)`
按实际止损位记账解决了 2N 虚高问题。

### 3.3 数据管道脚本（摘要，详见附录 A）

- **样板**：update_contracts / update_hots（当日幂等 + 原子替换 +
  .bak + 失败 notify + 顶层 traceback notify）；
- **update_hot_daily**：DSB 重建**无条件**每次执行（:212-216 注释自
  证 9/16"csv 已被别的路径写新而 DSB 落后"教训），但重启以
  `total>0` 为条件（:240）——两者口径不一致：他路径（手工回补/
  hots 换月）改 csv 后若增量为 0，DSB 重建了而 reader 缓存仍不刷新；
  且 `_restart_runner` 只在 `killed` 非空时 notify，**kill 零命中
  静默**（:268-271）；全量重建遍历目录内**所有** `_d.csv`（含非
  HOT 文件时会额外生成 his/day 文件）；
- **fetch_data_tqsdk**：`--fix-hots` 的 `to` 字段格式错误（实测
  `tq_to_wt_contract` 产 3 段式 `SHFE.rb.2601`，`split(".")[-1]` 得到
  `"2601"`；生产格式为 `"rb2701"`——测试同时固化了错误口径
  tests/test_fetch_tqsdk.py:74-79）。**该工具未在生产路径使用，属
  埋雷**；
- **pick_hot_sina --write / DataChecker.fix_hots / fetch_data_tqsdk
  .merge_hots**：非原子写 (+无备份)，与 update_hots 原子口径不统一；
- **fetch_data_sina**：`tempfile.mkdtemp` 临时目录泄漏 /tmp。

### 3.4 回测研究脚本

- **失败不阻断收集（P0）**：三者共同缺陷是"回测失败仍收旧产出"。
  具体口径各异：`run_walkforward.run_backtest` (:138-143) 只判
  `summary.json` 存在、**不查 returncode**——summary 由 WtBtAnalyst
  在跑完后写出，中途失败时上次产物残留即被静默当成本次结果（寻优/
  OOS 数据被上一窗口污染，无任何标记）；`run_matrix` 驱动层
  (:178-181) 检 returncode 但只 print FAILED、**不中断**，随后
  `collect` (:127-141) 仍读旧 summary；`run_slippage_sens.run_one`
  (:34-37) 只判输出目录存在（isdir），失败静默。三者均不校验产出
  新鲜度（mtime/窗口比对）。
- 子进程全部无 timeout；`run_speed_study` 有显式死代码
  (:232-237) 且把已算过的 sim_speed 又全量重跑一遍 (:241-248)。

### 3.5 部署与监控

- `deploy_tpl/run.py` 的 `WT_AUTO_REPAIR` 默认 off、`WT_PREFLIGHT`
  默认 warn，而 systemd units 均未设置这两个变量（仅有 monitor 设置
  WT_EXEC_RECOVER）→ **设计态"自愈 + strict 门禁"实际未生效**（除
  手工启动）；文档 DATA_OPS 与实现存在口径差。
- CSV 目录缺失仅 WARNING 后继续启动（:168-169）→ 静默退化到当初要
  绕过的 DSB 路径。
- 启动链合约同步是阻塞调用：run.py 包装层 `subprocess.run(timeout=660)`
  （unit 里 `--timeout 240` 是脚本内部 CTP 查询自限，两层不冲突）——
  合约同步卡住时启动链最长阻塞 11 分钟，恰逢 20:35/20:40 定时器
  kill 窗口会与 WatchDog 拉起争抢。
- 4 个 timer 全部 `Persistent=true`：服务器盘中重启会补跑 20:xx 任务
  → 立即 kill runDt/run.py（无交易时段保护、无 OnFailure 钩子）。
- `install_units.sh`：MON_TOKEN 缺省 `changeme`（8 字节会被 runMonSvr
  长度校验拒绝）；sed 未转义 `&`/`|`；TQ_PASS/TOKEN 明文写
  `/etc/systemd/system/*.service`（0644）；`User=ubuntu` 硬编码。

### 4.3 代码级小问题（业务相关）

  为准"，实际循环变量 `dirn` 取的是**最后一个**活跃子系统方向，注释
